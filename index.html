Node runtime · native layer in Rust

rsnode

A drop-in shaped Node runtime where the JavaScript engine and every builtin JavaScript file are the ones Node already ships, and only the native layer underneath is new.

Same engine. Same JavaScript. Native layer in Rust.

That sentence is the whole product, and also the whole limit: JavaScript runs at Node's speed here, because it is Node's JavaScript on Node's engine.

What this does and does not claim

A runtime page is a promise. These are the ones rsnode can keep, and the ones it cannot.

claim JavaScript execution is unchanged

V8 is the same engine and all 435 builtin lib/** files plus the three deps/ files are byte-identical to Node 28, frozen by sha256. A for loop, a Map, a regular expression, garbage collection: the same compiled JavaScript, running on the same engine.

If a workload is bound by JavaScript, rsnode's speed is Node's speed. No gain, no loss, by construction.

not claimed That startup is faster. It is currently slower.

rsnode reaches roughly 0.80x of Node on process startup — that is a ratio below 1, so it means Node is quicker: about 21.8 ms against 17.5 ms in the like-for-like empty-program case of the measured run. An earlier single-core run put the gap near 0.65x, because Node spreads its bootstrap over several threads and rsnode does not gain as much from that.

The startup work is not finished. The card above is the current number, not a target.

claim Some native paths were 10x slower, and that is fixed

Two native paths were genuinely broken, and both were found by running Node's own benchmarks rather than by guessing. Buffer#indexOf had no first-byte skip: 10.7x slower at the median and up to 191x on one configuration. TextEncoder#encodeInto wrote through the V8 API one byte at a time: 16.1x slower at the median.

Both are fixed and re-measured. Residuals remain and are stated with the numbers: encodeInto on long strings is still far behind, because Node calls simdutf where rsnode's write path is scalar.

not claimed That V8 is the identical minor version

The project's premise is "V8 unchanged", and across minor versions that is not currently true: rsnode links V8 15.2 while the Node 28 pin is 15.6. A pure-JavaScript null control — a loop that should measure identical on both runtimes — comes back at 1.000x on the fast-path medians, which is the result this project predicts and the one the control card above reports.

What differs is the shape of the distribution, not the throughput: in the measured run Node's first optimised pass lost a tier-up race on 13 of 30 runs while rsnode lost it on none. That is a startup and warm-up effect, not a per-operation speed difference, and the fast-path medians are what should be compared. Closing the V8 gap still means building V8 from source, not editing a version string.

What is deliberately not claimed here: that any of this is faster than Node on JavaScript, that rsnode competes with Bun on JS-bound work, or that compatibility is finished. Compatibility is measured against Node's own test suite and reported as a floor, not as parity.

What is actually wired up

rsnode is a native layer, so its coverage is measured in internalBinding() namespaces — the only door Node's JavaScript has into native code. This is what exists today, stated at the level the code supports rather than as a percentage.

Node's own JS, untouched

435 lib/** files and 3 deps/ files vendored byte-identical and hash-frozen. Editing one fails the build, so a native gap cannot turn into a JavaScript fork.

Binding contracts

contracts/ records the exact shape of each internalBinding() namespace from a real Node binary. rn-compat fails when a Rust namespace does not match, and a coverage ratchet stops a regression passing quietly.

Modules

CommonJS through Node's own 2297-line loader; ESM including top-level await and "type": "module".

I/O and processes

TCP, UDP, dns, net, http, child processes, MessagePort, and worker_threads on a real second isolate.

crypto

Real OpenSSL 3.6.3: DH, key objects, ciphers, X.509, signing, SecureContext, and the tls_wrap namespace wired on top. TLS is the newest surface and the least covered.

compression

zlib with zstd byte-identical to Node's, because it links the same C sources at the same version. deflate/gzip at levels 4–6 still compress worse than Node — a known, recorded divergence.

node:sqlite

A whole namespace, built on the same SQLite surface Node exposes.

Node-API

Prebuilt .node addons load through rn-napi, so third-party native modules are a target rather than an afterthought.

--permission

Genuinely enforces fs read/write, child and env. Does not yet enforce net, worker, addon, wasi, inspector or ffi, and the CLI says so instead of pretending.

The acceptance criterion is Node's test tree

The harness runs Node's own test/ files, one process per file, with a timeout — not a curated happy-path subset. Skips and node:test failures are scored as failures, and the denominator is corrected by running the same files under a real Node build. The pass rate is the compatibility card above.

One idea: move a layer, move nothing else

Bun replaces the engine, so it can be faster and has to reimplement Node's behaviour. rsnode does the opposite: it keeps everything that defines behaviour and replaces only the glue to the operating system.

The two top layers are identical, which is why compatibility is structural rather than a list of patched APIs: only the native layer can differ, and every failure this project has hit traced back to a native fact being missing or wrong — never to the JavaScript behaving differently.

One piece of C is kept on purpose. HTTP parsing stays on Node's generated llhttp state machine, compiled unchanged; only the V8 glue around it is Rust. Two parsers disagreeing about where a request ends is the request-smuggling vulnerability class, and that is not a place to rewrite for style.

Run your own code on it

The honest way to evaluate this is to point it at something you already care about. Node's test suite is the yardstick it is judged by, but your program is the one that matters.

build and run 
$ cargo build --release
$ ./target/release/rustnode ./your-program.js
$ ./tools/run-node-tests.sh --tests /tmp/node/test --filter test-fs-
